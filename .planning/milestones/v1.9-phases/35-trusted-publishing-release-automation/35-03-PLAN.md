<objective>
Add the production PyPI publish path so only version tags can publish through Trusted Publishing, and require an explicit `pypi` environment gate for the release job.
</objective>

<threat_model>
<assets>
- Production PyPI project for `corpulse`.
- GitHub release tags.
- GitHub `pypi` environment approval gate.
</assets>
<threats>
- HIGH T35-05: Production PyPI publishing can run from an arbitrary branch or manual workflow dispatch.
- HIGH T35-06: Production PyPI publishing bypasses human approval or equivalent explicit release gate.
- MEDIUM T35-07: Production PyPI publishing uses a long-lived PyPI token instead of Trusted Publishing.
</threats>
<mitigations>
- Guard the production publish job with `startsWith(github.ref, 'refs/tags/v')`.
- Set `environment: pypi` on the production publish job.
- Document required GitHub environment reviewer setup because environment protection rules are out-of-repo configuration.
- Use `pypa/gh-action-pypi-publish@release/v1` with job-scoped `id-token: write` and no token inputs.
</mitigations>
</threat_model>

Update `.github/workflows/release.yml` with a production `publish-pypi` job.

The job must:
- be named `publish-pypi`
- use `name: Publish to PyPI`
- use `runs-on: ubuntu-latest`
- declare `needs: build`
- include the exact tag guard `if: startsWith(github.ref, 'refs/tags/v')`
- declare `environment: pypi`
- declare job-level permissions:
  - `contents: read`
  - `id-token: write`
- use `actions/download-artifact@v4` with:
  - `name: python-package-distributions`
  - `path: dist`
- use `pypa/gh-action-pypi-publish@release/v1`

Do not set `repository-url` for the production job, so the action defaults to PyPI. Do not add `password`, `username`, `api-token`, `PYPI_API_TOKEN`, or `__token__`.
</action>
