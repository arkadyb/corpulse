## Active Roadmap: v1.8 Workload Observability and Replay Feasibility

### Phase 27: Workload Trace Feasibility and Schema Contract

**Goal:** Decide the minimal workload trace schema and implementation boundary before changing storage or APIs.
**Depends on:** Phase 26
**Requirements:** FEAS-01, FEAS-02
**Success Criteria:**
1. A feasibility record compares schema options against sync/async APIs, SQLite, Postgres, async Postgres, in-memory tests, privacy constraints, and dependency policy.
2. RAGPulse-inspired ideas are classified as implement now, defer, or reject with explicit reasons.
3. The selected MVP schema defines sessions, request identity, prompt components, token counts, timings, errors, and export semantics.
4. Replay scope is explicitly gated so implementation can stop at design/prototype if the trace foundation is not ready.

**Status:** Complete 2026-05-02

### Phase 28: Workload Trace Capture Foundation

**Goal:** Add durable sync and async APIs for first-class RAG request traces while preserving existing behavior.
**Depends on:** Phase 27
**Requirements:** TRACE-01, TRACE-02, TRACE-03, TRACE-04
**Success Criteria:**
1. `Corpulse.log_rag_request()` and `AsyncCorpulse.alog_rag_request()` can store sessionized request traces with components, token counts, optional timings, timeout state, and error state.
2. Prompt components support documented source taxonomy, token counts, references, and content hashes.
3. SQLite, Postgres, async Postgres, and in-memory paths have contract coverage for workload traces.
4. Existing retrieval, engagement, generation trace, report, cleanup, wrapper, and import behavior remains compatible.

### Phase 29: Workload Trace JSONL Import Export

**Goal:** Make workload traces portable for offline analysis, benchmark sharing, and later replay.
**Depends on:** Phase 28
**Requirements:** IO-01, IO-02, IO-03
**Success Criteria:**
1. Users can export workload traces as JSONL using a stable schema documented in README/API docs.
2. Users can import exported JSONL traces into supported storage backends.
3. Export works with hashes and references only; raw prompt/context/answer text is optional.
4. Round-trip tests prove imported traces preserve analytics-relevant fields.

**Status:** Complete 2026-05-04

**Plans:**
- Wave 1: `29-01` Shared workload trace JSONL codec
- Wave 2: `29-02` Sync JSONL import export facade; `29-03` Async JSONL import export facade
- Wave 3: `29-04` JSONL documentation and compatibility verification

### Phase 30: Workload and Serving Reports

**Goal:** Add workload and latency analytics that explain traffic shape, token pressure, component composition, and serving behavior.
**Depends on:** Phase 29
**Requirements:** WORK-01, WORK-02, WORK-03, SERV-01, SERV-02
**Success Criteria:**
1. Workload reports summarize request volume, throughput, burst windows, input/output token distributions, and long-context pressure.
2. Component reports show proportions for system prompt, vector DB context, chat history, web search, user input, file attachments, tool results, and other context.
3. Serving reports summarize TTFT, TPOT, total latency, stage latencies, percentiles, timeout rate, error rate, and slow-request contributors.
4. Reports remain inference-free and do not require LLM-as-judge dependencies.

**Status:** Complete 2026-05-04

**Plans:**
- Wave 1: `30-01` Workload report models and aggregation
- Wave 2: `30-02` Serving report models and aggregation
- Wave 3: `30-03` Public sync and async report APIs
- Wave 4: `30-04` Documentation and regression verification

### Phase 31: Session Analytics and Reuse Signals

**Goal:** Add session-level analytics for multi-turn RAG workloads and repeated context behavior.
**Depends on:** Phase 30
**Requirements:** SESS-01, SESS-02
**Success Criteria:**
1. Session reports summarize request count, turns per session, session duration, follow-up rate, and history growth.
2. Users can inspect repeated retrieval overlap and context reuse within sessions.
3. Analytics handle missing or sparse session IDs predictably.
4. Tests cover single-turn, multi-turn, repeated-context, and missing-session scenarios.

**Status:** Complete 2026-05-04

**Plans:**
- Wave 1: `31-01` Session report models and summary aggregation
- Wave 2: `31-02` Context reuse and retrieval overlap
- Wave 3: `31-03` Public sync and async session report API
- Wave 4: `31-04` Documentation and regression verification

### Phase 32: Replay Feasibility and Minimal Proof

**Goal:** Determine whether replay belongs in v1.8 implementation and, if feasible, add the smallest replay proof on top of exported traces.
**Depends on:** Phase 29
**Requirements:** REPLAY-01, REPLAY-02
**Success Criteria:**
1. A replay design explains OpenAI-compatible endpoint replay, timestamp scaling, callable-based replay, privacy implications, and benchmark result export boundaries.
2. If implementation is feasible, a minimal replay proof can replay exported traces through a user-provided callable without adding a mandatory model-client dependency.
3. If implementation is not feasible, the phase records the blocker and leaves replay as a future requirement without blocking completed workload observability features.
4. Replay decisions are reflected in PROJECT.md and REQUIREMENTS.md at phase completion.

**Status:** Complete 2026-05-05

**Plans:**
- Wave 1: `32-01` Replay feasibility decision record
- Wave 2: `32-02` Shared replay helper and sync facade
- Wave 3: `32-03` Async replay facade and docstring coverage
- Wave 4: `32-04` Replay documentation and regression verification
