# Requirements: corpulse v1.8

**Defined:** 2026-05-02
**Core Value:** RAG teams can point corpulse at their vector DB and immediately understand what's wrong with their corpus without manual audits.
**Milestone:** v1.8 Workload Observability and Replay Feasibility

## v1.8 Requirements

### Feasibility

- [x] **FEAS-01**: Maintainer can review a feasibility decision record that compares workload trace schema options against corpulse's existing storage, sync/async, backend, privacy, and dependency constraints.
- [x] **FEAS-02**: Maintainer can see which RAGPulse-inspired capabilities are approved for implementation now, deferred, or rejected with reasons.

### Trace Capture

- [x] **TRACE-01**: User can log a RAG request through sync and async APIs with timestamp, session ID, query, output token count, prompt components, optional timings, timeout state, and error state.
- [x] **TRACE-02**: User can represent prompt components as structured records with component type, token count, optional source references, and optional content hash.
- [x] **TRACE-03**: User can capture external context sources separately from local vector DB passages using a documented taxonomy.
- [x] **TRACE-04**: Existing retrieval, engagement, generation trace, report, and cleanup APIs continue to behave compatibly after workload trace support is added.

### Import Export

- [x] **IO-01**: User can export workload traces as JSONL using a stable, documented schema suitable for replay or benchmark sharing.
- [x] **IO-02**: User can import JSONL workload traces into supported corpulse storage backends for offline analysis.
- [x] **IO-03**: Export supports privacy-preserving operation by allowing content hashes and references without requiring raw prompt, context, or answer text.

### Workload Analytics

- [x] **WORK-01**: User can generate a workload summary report covering request volume over time, throughput, burst windows, and token distributions.
- [x] **WORK-02**: User can inspect prompt/component composition across requests, including proportions for system prompt, vector DB context, chat history, web search, user input, file attachments, tool results, and other external context.
- [x] **WORK-03**: User can identify long-context pressure from input tokens, output tokens, and component token share.

### Serving Metrics

- [x] **SERV-01**: User can summarize serving latency metrics including TTFT, TPOT, total latency, retrieval latency, rerank latency, generation latency, queue latency, timeout rate, and error rate.
- [x] **SERV-02**: User can inspect latency percentiles and slow-request contributors without requiring an LLM-as-judge or online inference dependency.

### Sessions

- [x] **SESS-01**: User can analyze sessions by request count, turns per session, session duration, follow-up rate, and history growth.
- [x] **SESS-02**: User can analyze repeated retrieval overlap and context reuse within sessions.

### Replay and Benchmarking

- [x] **REPLAY-01**: Maintainer can review a replay design or prototype that establishes whether OpenAI-compatible replay, timestamp scaling, and callable-based replay are feasible on top of the exported trace schema.
- [x] **REPLAY-02**: User can run a minimal replay proof only if the feasibility gate confirms it can be implemented without destabilizing the trace foundation.

## Future Requirements

### Optimization Signals

- **CACHE-01**: User can estimate prompt prefix reuse, passage reuse, session locality, query repetition, and likely KV-cache reuse opportunities.
- **CACHE-02**: User can receive recommendations such as reducing repeated low-engagement context or caching high-reuse prompt prefixes.

### Replay and Benchmarking

- **REPLAY-03**: User can compare before/after serving experiments and export benchmark result summaries.
- **REPLAY-04**: User can replay traces with richer concurrency controls and endpoint-specific adapters beyond OpenAI-compatible APIs and user-provided callables.

### Integrations

- **DB-01**: User can use a first-party Chroma wrapper on top of the generic wrapping surface.
- **DB-02**: User can use a first-party Pinecone wrapper on top of the generic wrapping surface.
- **DB-03**: Maintainer can package third-party wrapper recipes through a registry or plugin mechanism.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Full serving benchmark suite | This milestone must first prove the workload trace schema and minimal replay boundary. |
| Web dashboard | corpulse remains library-first; service/UI presentation belongs in the consuming service repo. |
| LLM-as-judge quality metrics | Existing project boundary keeps faithfulness, context precision, and answer relevance out of scope until explicit generation evaluation support exists. |
| Required raw prompt/context retention | Privacy-preserving hashes and references must be enough for analytics and export. |
| Universal wrapper support for all RAG frameworks | Framework plugins remain future work after the workload model is stable. |
