# Requirements: corpulse v1.9

**Defined:** 2026-05-15
**Core Value:** RAG teams can point corpulse at their vector DB and immediately understand what's wrong with their corpus without manual audits.

## v1.9 Requirements

Requirements for making corpulse installable from PyPI with verified optional extras and a repeatable release path.

### Package Metadata

- [x] **PKG-01**: User can view a PyPI package page for `corpulse` with accurate summary, README, license, Python compatibility, project URLs, and classifiers.
- [x] **PKG-02**: Maintainer can update one authoritative package version without `pyproject.toml` and runtime `corpulse.__version__` drifting.
- [x] **PKG-03**: Maintainer can build source distribution and wheel artifacts that include the intended package files, README, and license.
- [x] **PKG-04**: User can install the base package without optional integration dependencies being installed.

### Optional Extras

- [x] **EXTRA-01**: User can install Qdrant integration support with `pip install corpulse[qdrant]`.
- [x] **EXTRA-02**: User can import `corpulse` successfully when Qdrant, Postgres, FastAPI, pandas, and tabulate are not installed.
- [x] **EXTRA-03**: User gets actionable install guidance when using an optional integration without its required extra.
- [x] **EXTRA-04**: Maintainer can verify existing optional extras install cleanly from built artifacts in isolated environments.

### Release Automation

- [x] **REL-01**: Maintainer can run CI that tests, builds, and stores the exact sdist/wheel artifacts intended for release.
- [x] **REL-02**: Maintainer can publish to TestPyPI from GitHub Actions using PyPI Trusted Publishing.
- [x] **REL-03**: Maintainer can publish tagged releases to PyPI from GitHub Actions using PyPI Trusted Publishing.
- [x] **REL-04**: Maintainer can protect PyPI publishing behind a GitHub environment or equivalent explicit release gate.

### Documentation and Validation

- [x] **DOC-01**: User sees `pip install corpulse` as the primary installation path in README/docs.
- [x] **DOC-02**: User sees `pip install corpulse[qdrant]` as the primary Qdrant installation path in README/docs.
- [x] **DOC-03**: Maintainer has a release checklist covering version bump, build, TestPyPI validation, PyPI publish, and post-publish smoke checks.
- [x] **VAL-01**: Maintainer can verify a clean environment install from the published PyPI package.
- [x] **VAL-02**: Maintainer can verify a clean environment install from the published `corpulse[qdrant]` extra and instantiate/import the Qdrant wrapper surface.

## Future Requirements

Deferred to a future release.

### Release Maturity

- **REL-05**: Maintainer can generate release notes automatically from merged changes.
- **REL-06**: Maintainer can publish signed artifacts beyond the provenance provided by Trusted Publishing.
- **REL-07**: Maintainer can track PyPI download/adoption analytics in project reporting.

## Out of Scope

Explicitly excluded from this milestone.

| Feature | Reason |
|---------|--------|
| New vector database adapters | v1.9 is about distribution readiness, not integration expansion. |
| CLI command surface | Existing library API should remain the focus for the first PyPI release. |
| Web dashboard | Not needed to make the package installable and verifiable. |
| API-breaking package restructure | The first PyPI publish should minimize user-facing import churn. |
| Full release-note automation | Useful later, but the first release only needs a reliable checklist. |
