<context>
The milestone intentionally favors metrics that can be derived from stored retrieval and engagement data with no new schema or ingestion surface.

Relevant implementation facts:
- `Corpulse.log_engagement()` already records free-form engagement labels.
- `engagement_counts(since)` returns per-document engagement aggregates and is already consumed by suspects, report output, and cleanup logic.
- All backends already expose the same aggregate surfaces across SQLite, Postgres, async Postgres, and in-memory implementations.
- Phase 22 already established the pattern for scalar metrics: backend-owned aggregation plus a thin pure helper in the facade layer.

The metric definition must be explicit in tests because the schema does not store user IDs, sessions, or per-query acceptance labels. The chosen Phase 23 definition is row-level:
- count engagement rows whose normalized `event_type` matches the shared accepted-event convention
- divide by total engagement rows in the same lookback window
- return a scalar float rounded to 2 decimals
- return `0.0` when there are no engagement rows in the window

The accepted-event convention is fixed for v1.5 rather than user-configurable. The phase should document and test a small positive-action allowlist derived from the current docs/examples, normalized once in shared code, and counted as non-accepted otherwise. [ASSUMED: the concrete allowlist is frozen in the plan and tests, not exposed as public API]
</context>
