<context>
Phase 24 builds the capture-only half of the v1.6 milestone. The phase should treat generation traces as immutable evaluation records, not as corpus-health metrics and not as user/session analytics.

Relevant implementation facts:
- Phase 23 already established the additive-contract pattern for a new analytic surface on top of existing storage backends.
- Existing backend methods already use typed row contracts and deterministic ordering where parity matters.
- Sync and async facades in this repo are thin orchestration layers over backend reads and writes.
- The current codebase has no trace capture primitives, so all trace semantics must be introduced explicitly and tested from scratch.

Design decisions locked for this phase:
- Use one new `GenerationTraceRow` typed row for a single generation event.
- Store prompt/query text, context refs, final answer text, optional evaluation labels, and captured-at timestamp.
- Keep trace records append-only and independent of document deletion.
- Return trace rows in deterministic chronological order so future metrics can consume them without ambiguity.
- Keep existing retrieval, engagement, report, cleanup, and analytics behaviors unchanged.
</context>

|----------|-------------|
| public trace API -> backend storage | Trace capture accepts raw prompt/answer text and optional labels, but must store them in a deterministic, append-only shape |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-24-03 | Repudiation | append-only logs | mitigate | Keep trace storage append-only and independent of document deletion so future evaluation data remains auditable |
</threat_model>
